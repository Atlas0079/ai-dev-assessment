# ORDER接口与检查边界 2.0

沿用起始工程的Java8、Spring Boot 2.1.13、Maven两模块、MongoTemplate及既有DAO接口。不能把服务替换为只响应固定测试数据的脚本。

成功接口HTTP200，统一包装 {"code":0,"data":结果}；错误返回HTTP错误状态与字符串code。健康接口直接返回status=ok，可附加storage。登录 POST /v1/demo-login，输入 {"account":"customer1"}，返回token；四种演示身份为customer1/customer2/provider1/provider2。受保护接口使用Bearer令牌。

GET /v1/services 返回服务数组；s1的amountFen=3000。POST /v1/orders 输入serviceId=s1，客户端amountFen不可信，返回订单。GET /v1/orders/{id}返回授权可见订单。GET /v1/orders?page=1&size=2返回items与total，页码从1开始。详情返回id、customerId、providerId、serviceId、status、amountFen、version，不泄露内部幂等回执。

POST /v1/orders/{id}/accept、cancel、complete 接收 {"note":"备注"}，Idempotency-Key请求头必填。状态规则见任务.md。同身份/订单/动作/key和相同note返回首次成功结果，不同note冲突409。初始version=0，每次成功迁移+1；不合法状态409、越权403、不存在404、未登录401。非本人订单详情允许403或404。

检查器会写入多笔虚构订单，应连接专用、无其他并发业务的测试数据库。不要指向公司业务数据库。分页检查会读取测试账号全部订单，上限10000笔；每次验证推荐空数据库。

O17需要评测方控制MongoDB故障注入并直接读取最终订单；O18需要评测方控制进程重启。只有HTTP地址时这两项输出NOT_RUN，不能据此判候选人失败。控制接口不由候选人额外提供；沿用可信执行器的数据库/进程控制。

当前O17模拟一次MongoDB update连接中断，然后使用相同幂等key重试并读取数据库。它不覆盖所有提交时刻的网络分区、事务、数据库重启或消息丢失。O18验证单进程重启后的订单内容和幂等回执。

本版不检查真实支付、微服务对接、iOS/Flutter客户端、Java代码质量或生产级高并发。10轮两请求竞争属于功能性检查，不是压力测试。
