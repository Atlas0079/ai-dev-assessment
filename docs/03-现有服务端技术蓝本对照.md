## 1. 结论

平台开发题应以现有新订单链路的组织方式为蓝本，独立编写可对外提供的小型模拟项目。最重要的修正是：本次查看的 `newOrder` 订单链路使用 MongoDB 和 MongoTemplate，不能因为模块 POM 中有 MySQL/MyBatis 就把这条链路设计成关系数据库练习。

此前详细设计中的 Java 21 + Spring Boot 3.x + PostgreSQL 是未查看公司项目时的建议，不能继续视为已对齐的技术基线。现有业务规则、评分权重仍可作为草案，但存储、工程分层和原子性验收需按下述方向修订后再实施。

## 3. 考试项目建议保留什么

建议工程结构：

```text
assessment-order/
  pom.xml
  order-api/
    dto/vo/entity/enums/service
  order-application/
    controller/
    service/impl/
    dao/
    statemachine/
    config/
    support/
  compose.yaml
  README.md
```

保留的学习和考察重点：

- 候选人阅读已有Request/VO和Service契约，再修改实现。
- Controller从统一用户上下文拿身份，不能信任请求体用户编号。
- Service组织业务规则，DAO执行Mongo条件更新。
- 沿用统一响应和异常处理模式，但使用独立编写的轻量实现，不复制私有工具包。
- 用小型状态转换表体现非法迁移与操作者约束。
- 给定列表、详情、创建等现成能力，要求新增流转时保持原有功能。
- 测试使用真实数据库检查竞争后的结果，不只检查接口返回成功。

建议仅维护一套模拟项目公开接口，候选人修改已有入口；不同时维护REST风格和公司路径风格两套兼容API。实际路径与响应字段在题包发布前统一冻结，不直接把整套公司业务接口搬出。

## 4. 需要简化的部分

| 公司项目元素 | 考试建议 | 原因 |
|---|---|---|
| Java8 / Boot2.1.13 | 如追求上岗环境一致，题包采用经验证的同代环境；精确补丁版本实施前冻结 | 不把运行版本误写成Java21；也不自动复制全部依赖版本 |
| MongoDB | 必需，提供本地容器与虚构seed | 与被考察的新订单链路直接相关 |
| Redis / Redisson | 可提供预配置实例和薄封装，评分不强制某种锁实现 | 可考察现有调用方式，避免让候选人先搭基础设施 |
| Dubbo | 保留Java服务接口边界，首版使用进程内实现 | 单题无需注册中心和多服务RPC |
| Nacos | 题包用本地配置和环境变量 | 不能要求访问公司配置中心 |
| RabbitMQ / Kafka | 一期没有必考异步需求时不引入 | 当前接单/取消/完成题无需复制全平台消息系统 |
| 支付、IM、用户中心 | 用题包提供的本地模拟实现 | 不接真实业务、不需要私有SDK |
| 公司基础镜像及私服 | 独立、可获取、锁定版本的题包镜像与依赖 | 候选人可在规定环境复现 |
| 多维复杂订单状态 | 一期保留简化履约状态，支付模拟固定已支付 | 能在两天窗口完成，不把四套状态机全部转给实习生 |

保留Java8不意味着给新项目编写一套兼容旧数据的逻辑。考试数据直接适配冻结的模拟系统。评测执行器与候选人应用分离，不要求评分系统也使用公司老服务的所有框架和版本。

## 5. 对原详细设计的具体修订清单

1. 技术选型：ORDER改为参考Java8/Spring Boot现有代际、Maven多模块、MongoTemplate/MongoDB；精确镜像需实际验证后冻结。
2. 分层：起始仓库分成order-api、order-application，提供轻量统一响应、用户上下文与状态转换表。
3. 并发：从“必须处于同一关系数据库事务”改成“对外操作及幂等结果具有一致、可恢复的效果”。建议把简化订单状态、version和少量操作幂等记录放在同一文档中原子更新，避免强制多文档事务。
4. 故障验收：O13检查无部分状态、结果不确定时可重试核验；不要求具体SQL提交/回滚机制。模拟代理需要兼容MongoDB协议或采用可控的连接级故障注入。
5. 数据：以集合及索引初始化替代建表；持久化检查读取独立测试Mongo实例；不使用公司数据。
6. Redis锁只辅助协调。即使加锁，也须通过数据库条件更新保持竞争正确；不以是否用了Redisson加减分。
7. 现有四个状态维度提供给出题者理解业务，候选人一期仅处理明示的简化规则，不能隐藏考察真实公司规则。
8. UNO与AI提效方向继续按原原则开放技术栈，不因平台Java技术栈而强制三个任务都用Java。

以上为针对实际仓库的修订建议，尚未执行代码修改。第一版两份文档仍保留原始评审内容；本补充文档标明其技术假设中需要调整之处，实施前应合并为统一版本。
